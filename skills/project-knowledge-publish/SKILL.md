# 目的

`project-knowledge/` のナレッジを、人間向けドキュメントとして出力する。

元ナレッジは変更しない。

# 対象

ユーザーの依頼から出力範囲を判断する。

例:

- 「プロジェクトナレッジを出力して」
  - 全体

- 「認証に関する部分だけ出力して」
  - 認証に関連する内容のみ

- 「Firebaseとデプロイについてまとめて」
  - 指定テーマに関連する内容のみ

- 「システム構成を説明して」
  - アーキテクチャ・構成に関連する内容のみ

範囲が指定されていない場合は全体を対象とする。

# 読み込み

1. `project-knowledge/index.md` を読む。
2. ユーザー指定テーマに関連するナレッジを特定する。
3. 必要なリンク先だけ読む。
4. 全体出力の場合も `index.md` から辿れるナレッジを対象とする。
5. `pending.md` は原則として公開内容に含めない。ユーザーが未確定事項や設計判断などを要求した場合のみ、必要な部分を使用する。

コード、設定、外部環境は再調査しない。現在の `project-knowledge/` だけを入力データとする。

# 出力

AI 向けの圧縮表現をそのまま転記せず、人間向けに再構成する。

次の方針に従う:

- 意味が分かる見出し構成へ整理
- 略記・キー値表現を自然な説明へ変換
- 関連情報を統合
- 重複を除去
- 必要に応じて箇条書き・表を使用
- 読み手に不要な内部メタデータを除外
- 内容の意味は変更しない

# 出力形式

出力ごとに新しいフォルダを作り、その中へ Markdown ファイルを保存する。

出力先の指定がない場合は、リポジトリルートに `project-knowledge-published-YYYYMMDD-HHmmss/` を作る。日時には実行環境のローカル時刻を使用する。

ユーザーが出力先を指定した場合も、そのフォルダを新規作成する。指定先がすでに存在する場合は上書きしない。末尾に `-YYYYMMDD-HHmmss` を付けた別のフォルダを作る。

出力フォルダは以下の構成にする:

```text
project-knowledge-published-YYYYMMDD-HHmmss/
├── index.md
├── overview.md
├── architecture.md
└── operations.md
```

`index.md` は必須とし、次の内容を含める:

- 文書全体のタイトル
- 対象範囲またはテーマの短い説明
- 作成したすべての個別 Markdown ファイルへの相対リンク
- 各リンク先の内容が分かる一文の説明

個別ファイルは、内容のまとまりごとに分割する。ファイル数は固定しない。情報量が少ない場合でも、`index.md` とは別に1つ以上の個別ファイルを作る。

個別ファイルの名前には、内容を表す英小文字の kebab-case を使用する。拡張子は `.md` とする。

`index.md` からのリンクは、次のような同一フォルダ内の相対リンクにする:

```markdown
- [概要](./overview.md): プロジェクトの目的と主要機能
- [システム構成](./architecture.md): コンポーネントと連携関係
```

個別ファイル間に関連がある場合は、必要に応じて相対リンクを追加する。元の `project-knowledge/` にあるファイルパスを、公開文書のナビゲーションにそのまま流用しない。

以下は通常出力しない:

- YAML frontmatter
- `type`
- `tags`
- `sources`
- OKF内部構造
- ファイル配置情報
- AI向け運用指示
- `pending.md` の未確定事項
- 秘密情報

# テーマ指定

テーマ指定時は、ファイル名だけで対象を判断しない。

各ナレッジの内容、リンク、関連概念を確認する。そのうえで、テーマに関連する情報を抽出する。

例:

「認証」の場合、必要に応じて以下を横断する:

- `architecture.md`
- `system.md`
- `integrations/firebase.md`
- `api.md`

ただしテーマと無関係な内容は出力しない。

# 情報の扱い

- ナレッジに存在しない情報を推測で補わない。
- 複数ファイルの内容が重複する場合は統合する。
- 矛盾する記述がある場合は勝手に解決せず、その旨を明示する。
- 不明・未記載事項を必要以上に補足しない。
- 人間向けとして意味のない実装詳細は省略してよい。
- ただし重要な仕様・制約・設計判断は省略しない。

# 詳細度

ユーザー指定を優先する。

指定がない場合:

- 概要だけではなく、プロジェクトを理解できる情報量を確保する。
- 冗長な説明は避ける。
- 同じ事実を複数回説明しない。

例:

- 「簡潔に」: 要点中心
- 「詳しく」: 関連する仕様・制約・構成を詳細化
- 「概要」: 主要項目のみ
- 「そのまま資料に使える形」: 文書として自然な構成に整える

# 出力先

`project-knowledge/` 配下には出力しない。

出力後の応答では、作成したフォルダと `index.md` のパスを示す。文書全体を応答本文へ重複して掲載しない。

# セキュリティ

元ナレッジに秘密情報と思われる値があっても出力しない。

除外対象:

- パスワード
- APIキー
- アクセストークン
- 秘密鍵
- credentials
- その他の認証秘密

環境変数名や非秘密の設定情報は、必要に応じて出力可能。

# 完了確認

出力前に確認する:

- 指定テーマから逸脱していない
- 関連するナレッジの読み漏れがない
- 元ナレッジにない事実を追加していない
- AI向け内部表現を不要に露出していない
- 重複がない
- 秘密情報を含まない
- 人間が単独で読んで理解できる
- 新しい出力フォルダ内に `index.md` が存在する
- `index.md` からすべての個別 Markdown ファイルへ相対リンクで辿れる
