# Publishing

ナレッジをsource of truthのまま保持し、成果物は`published/`へ再生成する。公開物からナレッジへ逆同期しない。

公開はファイルの複製ではなく、Knowledgeの意味を保ったまま読み手向けに編集する工程である。読みやすさを優先するが、変更すること自体を目的にした言い換えや、説明量を増やすだけの冗長化はしない。

## 出力と対象範囲

既定ではMarkdownとoffline HTMLの両方を生成する。ユーザーが出力形式または対象範囲を指定した場合は、その実行だけに適用し、Knowledge Baseへ永続化しない。

- Markdown: `docs/`を人間向けに再構成し、`published/markdown/`へ出力する。User StatementやInteraction RecordなどのRaw Referenceを無条件に公開しない。
- HTML: このSkillの`scripts/build_offline_docs.py`を`uv run`で実行し、Markdown成果物からMaterial for MkDocsによる`published/html/index.html`を生成する。スクリプトは`file://`ナビゲーション、ローカル検索、CDN非依存、broken linkを検証する。

対象範囲の指定がない場合は、`docs/index.md`から辿れる通常Conceptを対象とする。関連するKnowledgeは、`index.md`、必要なカテゴリの`index.md`、個別文書、その文書が根拠とするReferenceの順で読む。Raw Referenceは事実確認に使用できるが、全文や内部記録をそのまま公開しない。

## Project Artifactによる現在構造の補完

Knowledgeには持続的な設計意図、制約、理由、仕様を求め、現在の作業ツリーにあるProject Artifactからは公開時点の実装構造を補う。Project ArtifactはKnowledgeのsourceとして登録されているファイルだけに限定せず、公開対象の理解に必要な現在のソースコード、設定、manifest、ビルド定義、公開インターフェースなどを直接確認する。

調査範囲と詳細度はユーザー指定を優先する。指定がない場合はKnowledgeの公開対象と読み手の理解に必要な範囲から、入口、主要モジュールやpackage、公開API、主要な依存関係、関連設定を選ぶ。ディレクトリ構成、宣言、import、呼び出し関係、設定値などから直接確認できる事実、または機械的に導出できる構造だけを使う。全ファイル、全クラス、全メソッドを無差別に列挙せず、生成物、依存物、キャッシュ、秘密情報を調査・公開対象から除く。

補完時は次の境界を守る。

- 観測した構造は読み手に合わせて自然文、表、簡潔な一覧へ整理できる。ただし、実装から確実に判断できない意図、採用理由、仕様、将来方針を推測しない。
- Knowledge由来の設計意図や制約と、Project Artifact由来の現在構造を組み合わせる。由来が解釈に影響する箇所は、「Knowledgeに記録された方針」「現在の実装で確認できる構造」のように区別し、Project Artifactの根拠パスを示す。
- KnowledgeとProject Artifactに明確な不一致がある場合は、どちらかへ統合・上書きせず、「Knowledgeの記載」「現在のProject Artifact」「確認した根拠」を並べて差異を示す。限定的な検索で見つからないことだけを不一致の根拠にしない。
- 補完内容と不一致は公開成果物だけに記載する。`docs/`、User Statement、Interaction Record、Reference、`knowledge-policy.md`、`state.yml`へ逆同期しない。
- 鮮度回復が必要でも、`update`、`verify`、`fix`、`audit`、`refactor`を自動実行しない。必要なら完了報告で別操作として案内する。

補完条件は出力形式や対象範囲と同じ実行時指定として扱う。汎用コードインデックスや構造キャッシュを作らず、公開の都度、必要なProject Artifactを現在の作業ツリーから確認する。

## Markdownの編集手順

文書ごとに読み手、目的、前提を確認し、元のファイル境界や記載順をそのまま公開構成とみなさない。関連情報は必要に応じて統合し、異なる目的を持つ情報は分ける。公開した全ページは`index.md`から相対リンクで辿れるようにする。

次の規則で文章を再構成する。

- 文書の目的と前提が分かる導入を置き、概要、利用方法、制約、詳細のように読み手が理解しやすい順序へ並べる。
- 内容を表す具体的な見出しを使い、元Knowledgeの機械的な章立てやファイル配置を露出しない。
- 略記・キー値表現・圧縮された箇条書きを、主語と関係が分かる自然な説明へ変換する。
- 専門用語、コード識別子、設定名は正確な表記を保ち、初出時に役割や文脈を添える。
- 理由や因果関係は文章で説明し、比較や手順など一覧性が重要な情報には箇条書きや表を使う。
- 複数文書に分散した関連情報を統合し、同じ事実の繰り返しを除く。
- YAML frontmatter、`pk_category`、`pk_derivation`、`sources`、生成履歴、ファイル配置など、読み手に不要な内部メタデータを除く。

元文書がすでに品質ゲートをすべて満たす場合は、内容を維持してよい。その場合も文書ごとに評価し、機械的なコピーで済ませない。変更目的だけの言い換えは避け、維持した理由を完了報告へ記載する。

## 情報の正確性

- Knowledgeに存在しない事実を推測で補わず、内容の意味を変更しない。
- 重要な仕様、制約、設計判断、例外、正確な識別子を省略しない。
- 矛盾や不確定事項は勝手に解決せず、読み手が判断できる形で明示する。
- Knowledgeと現在のProject Artifactの明確な不一致は、双方の内容と根拠を区別して明示する。
- `status`、`verified`、`stale`などが解釈に影響する場合は、生のキー値ではなく「確認済み」「要再確認」などの人間向け注記として表現する。
- パスワード、APIキー、アクセストークン、秘密鍵、credentialsなどの秘密情報を出力しない。

トークン数の削減や増加を成功条件にしない。必要な説明を欠かさず、同じ事実の反復や過剰な前置きを避け、理解しやすさと簡潔さを両立する。

## 文書単位の品質ゲート

各文書を出力する前に、次をすべて確認する。

- 単独で読んでも、その文書の目的、対象、前提が分かる。
- 見出しと説明順が、元ファイルの都合ではなく読み手の関心に沿っている。
- AI向け内部表現、未説明の略記、生のメタデータが残っていない。
- 公開対象の重要情報が欠落しておらず、同じ説明が不要に重複していない。
- 専門用語や識別子に、理解に必要な文脈がある。
- 推測、意味変更、秘密情報の混入がない。
- Project Artifactによる補完がある場合は、現在構造の根拠を追跡でき、Knowledge由来の意図や制約と混同していない。
- Knowledgeとの不一致を隠した統合や上書きをしていない。
- 関連ページへのリンクが公開物の中で解決できる。

品質ゲートを満たさない文書は、そのまま出力せず再編集する。元文書を維持する場合は、すべての項目を満たすことを確認する。

## offline HTMLの生成

実行例は `uv run <skill>/scripts/build_offline_docs.py project-knowledge/published/markdown project-knowledge/published/html`。既存の非空出力先を置換する場合は事前承認を得てから`--force`を付ける。HTML生成処理をナレッジ生成へ混ぜない。

形式1.0だけをread-onlyで扱う。通常Conceptの分類、verified、status、staleを必要に応じて人間向けに表現し、Raw ReferenceはKnowledge分類の対象外とする。形式が異なる場合は生成せず、対応Skillの更新が必要と報告する。

## 完了報告

公開後は次を報告する。

- 生成した形式と出力先
- 再編集した文書と主な編集内容
- 内容を維持した文書と、そのままで品質ゲートを満たすと判断した理由
- 公開対象から除外した文書と理由
- Project Artifactから補完した構造、その調査範囲、主な根拠
- KnowledgeとProject Artifactの不一致。ない場合は、調査範囲で明確な不一致を検出しなかったこと
- HTMLを生成した場合は、`index.html`、ページ数、画像数、警告数、broken link数
