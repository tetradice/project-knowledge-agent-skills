# 情報源と調査

## 正本の優先順位

ナレッジと実際の状態が競合する場合は、次の順序で判断する。

1. 現在のコードと設定
2. 現在の外部環境
3. Git の状態、diff、log
4. `project-knowledge/pending.md`
5. その他のプロジェクトナレッジ

会話履歴は補助情報とする。コード、設定、Git などから復元できる情報では、会話履歴を正本にしない。

## Git 状態

`init` または `update` でファイルを変更する前に、次を確認する。

1. bundle を含む Git リポジトリのルートを特定する。
2. `git rev-parse HEAD` で完全長 40 文字の SHA を取得する。
3. 作業ツリーが dirty か確認する。

Git 管理外や初回コミット前で SHA を取得できない場合は、ファイルを変更せず中断する。作業ツリーが dirty でも処理は続け、完了時にその事実を報告する。

`check` では Git 履歴を利用できなくても検証を続ける。利用できなかった理由を完了時に報告する。

## 調査範囲

1. `project-knowledge/index.md` を読む。
2. ユーザー依頼から関連するコンセプトを特定する。
3. 関連コンセプトの `sources` と `resource` を確認する。
4. `git_base_commit` が有効な場合は、そこから現在の `HEAD` までの差分を調査範囲の手掛かりにする。
5. 関連するコードと設定だけを調査する。
6. 必要な場合だけ外部環境を確認する。
7. 試行錯誤、一時状態、revert 済みの状態を無視する。
8. 最終的な状態だけを対象とする。

`git_base_commit` からの差分だけを正本にしない。現在のコード、設定、`sources` も確認する。コミットが存在しない場合や履歴を辿れない場合は、その事実を報告して通常の調査を続ける。

ナレッジ全体を毎回無条件に読み直さない。

## 外部環境

Firebase、AWS などの外部環境は、必要かつアクセスできる場合だけ確認する。

確認できない情報は推測しない。既存値を無条件に正しいとみなさず、確認できなかったことを報告する。
