# 記述形式と配置

## 基本形式

ナレッジのルートには `project-knowledge/` を使用する。

次の形式で記述する。

- OKF v0.2
- Markdown + YAML frontmatter
- AI が解釈できる最小限の記述
- 長文よりも見出し、箇条書き、キーと値を優先した構成

人間向けの説明文は追加しない。

## ディレクトリ構造

次のファイルを必須とする。

- `index.md`: ナレッジ索引
- `pending.md`: 後から復元できない未反映情報

その他のファイルは必要に応じて作成する。

例:

- `system.md`: 小規模プロジェクトの統合仕様
- `architecture.md`: 構成、責務、境界
- `runtime.md`: 実行、ビルド、デプロイ、環境
- `integrations/`: 外部サービス
- `data-model.md`: データ構造
- `api.md`: API 仕様

利用先プロジェクトの `project-knowledge/references/` は任意とする。
このディレクトリには、人間または外部から明示的に与えられ、継続して信頼する **trusted raw sources** を配置する。
Skill 自身の手順を格納する `skills/project-knowledge/references/` とは別のディレクトリである。

配置例:

- `references/requirements/`: 要件、仕様、業務ルール
- `references/environment/`: コードから取得できない環境情報
- `references/external/`: 外部サービス仕様、ベンダー資料
- `references/decisions/`: 人間が確定した設計方針、設計判断

サブディレクトリは例であり、必須ではない。
Markdown に限定せず、`.md`、`.txt`、`.json`、`.yaml`、`.yml` など、エージェントが安全にテキストとして解釈できる資料を扱う。

`references/` は生成ナレッジではなく入力となる Raw Source である。
配下の資料を OKF コンセプトとして扱わず、原則として個々の資料を `index.md` のコンセプト一覧へ列挙しない。
通常の `init`、`check`、`update` では内容、形式、ファイル名、配置を変更せず、削除もしない。
ユーザーが資料自体の変更を明示した場合だけ、その依頼を通常 operation とは分けて扱う。

ファイルを過剰に分割しない。ファイルが肥大化した場合や、独立した概念が生じた場合だけ分割する。

## index.md

ルートの `index.md` には、次の frontmatter を記述する。

```yaml
---
okf_version: "0.2"
---
```

本文には、各ナレッジへのリンクと短い説明だけを記述する。

```md
# コア
- [システム](system.md) - 現在のシステム仕様。

# 作業中
- [未反映事項](pending.md) - 後から復元できない未反映情報。
```

原則として `index.md` から参照を始め、必要なファイルだけを読む。

## ナレッジ本文

本文には、後続作業に必要な現在の実装や環境状態に加え、trusted raw sources に定義された安定した要件、制約、設計判断を記述できる。
異なる種類の情報を同じ状態に統合せず、要件と現在実装が異なる場合は両方と不一致の状態を残す。

```md
# 認証

- 要件: Google ログインを提供する
- 現在実装: 未実装
- 状態: 要件と実装が不一致
- 未ログイン利用: 可能
```

長い説明文は避ける。

## 情報分類

次の情報を記録する。

- 現在のシステム仕様
- アーキテクチャ
- 重要な制約
- 外部サービス構成
- 実行、デプロイ環境
- コードから自明でない設計判断
- trusted raw sources に定義された要件、業務ルール、制約
- 要件、設計判断、現在実装、現在の外部状態のあいだにある差異
- AI が後続作業で必要とする情報

次の情報は原則として記録しない。

- 一時的な実装状態
- 試行錯誤
- revert 済みの変更
- 作業日誌
- 詳細な変更履歴
- ソースコードから容易に復元できる冗長な説明
- 秘密情報

## pending.md と trusted raw sources

`pending.md` には、後から復元できず、正式な安定情報源へまだ統合されていない一時的な情報を置く。
セッション中に決定した設計理由、コードへ未反映のユーザー決定、将来必要になる重要前提が該当する。

`references/` には、人間が明示的に管理する継続的な Raw Source を置く。
正式な要求仕様、業務ルール、確定済み設計判断、外部サービス仕様、コード外の環境定義が該当する。
`pending.md` の内容を `references/` へ自動移動しない。
`pending.md` は正式な OKF コンセプトへ統合できるが、`references/` は人間管理領域として保持する。

## セキュリティ

次の値を保存、表示、報告しない。

- パスワード
- API キー
- アクセストークン
- 秘密鍵
- 認証情報
- `.env` の値

必要な場合は、変数名、用途、取得元、非秘密メタデータだけを記録する。
この規則は `project-knowledge/references/` の調査にも適用する。
資料に秘密値が含まれていても、ナレッジや完了報告へ転記しない。
ファイルパス自体が秘密でなければ、秘密値を含む資料のパスを `sources.resource` に記録できる。
