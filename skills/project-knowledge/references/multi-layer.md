# 複数レイヤーの確定定義と配置表

`init`と`split`だけで使う共通入力契約である。[ルート設定](project-config.md)の形式・版は変えない。
意味の分類とPolicy適合はAIが判断し、設定・配置・参照書換え・切替は補助スクリプトへ渡す。

## 定義を固定する

利用者の明示値を優先する。レイヤー数・用途の指定がなければ単一初期化を維持する。複数指定の境界が不明な場合だけ用途と保存対象を質問する。十分な指定がある場合は再承認を必須にしない。

| 項目 | 新規の既定値と制約 |
| --- | --- |
| `id` | 用途から有効なIDを一度生成して固定。既存IDは変更しない |
| `name` | 用途を表す一意の名称。既存値は指定がなければ維持 |
| `path` | `default`は`./project-knowledge`、その他は`./project-knowledge-<id>`。既存は維持 |
| `description` | 保存する情報と他レイヤーへ送る情報を具体化。複数構成ではdefaultにも必須 |
| `access` | 明示的に`read-write`。指定値と既存の権限を優先 |
| `optional` | `false`。作成途中の欠落を隠すためにtrueを使わない |
| `auto_select` | `true`。機密用・手動指定専用など明示用途があればfalse |
| `write_target` | 新規複数構成は明示的にnull。既存設定は解決済み値を維持。明示指定を優先 |

新規パスは相互および既存レイヤーと同一・入れ子にしない。定義は入力順、ファイル処理は相対パス順とする。新規制限を既存設定全般の仕様変更へ広げない。
スクリプトにはIDを確定済みで渡す。実行中や再開時にID・パス・用途を再生成しない。

```json
{
  "layers": [
    {"id": "product", "name": "製品仕様", "description": "利用者向け機能と業務ルールを保存。実装判断と運用手順は開発・運用へ送る"},
    {"id": "development", "name": "開発・運用", "description": "実装判断と運用手順を保存。利用者向け仕様は製品仕様へ送る"}
  ],
  "write_target": null
}
```

## 配置を固定する

1. 利用者指定の文書・ディレクトリ対応を優先する。
2. 明示対応がなければ主題と保存・除外対象を照合し、適合先が一つの場合だけ採用する。
3. 初期化の未決定は保存先を質問する。分割では元を残せる場合だけ未決定・複数主題の文書を元に残す。本文を分割しない。
4. 境界に重複があれば境界を直してから表を確定する。Conceptの同じ主張を複製しない。
5. 配置表は元ファイルまたは収集候補、移管先ID、移管先相対パス、理由、依存Referenceを持つ。`write_target`で初期収集・移行先を決めない。

入力JSONと`.project-knowledge-operation/`の記録は操作用の一時情報であり、ルート設定やstateへ移行項目を追加しない。秘密情報を収集しない。記録には復旧用の原本が含まれるため公開・コミットしない。
`sources[].resource`の正規基準は`docs/`。既存の文書相対sourceは、docs基準の実体がない場合だけ互換解決する。splitでは解決した実体を維持してdocs基準へ変換し、無関係な既存文書を一括変更しない。
完了時は復旧用コピーを消し、再実行用の指紋と結果を残す。次の別操作を始めるときは完了記録を確認して、この操作の一時ディレクトリだけを明示的に片付ける。

## 通常運用との境界

分割後は全件を参照し、出典レイヤーを示す。書込みは現行順序（明示ID、明確なname/ID、用途とPolicyに適合する一意候補、write_target）で一つに限定する。決まらなければ質問する。
複数領域の更新は対象IDを持つ個別更新へ分ける。共有Referenceは自動同期せず、sourceと移行記録から更新影響先を確認する。通常updateから自動分割・移動を起動しない。
